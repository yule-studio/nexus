# Insecure Design (OWASP A04) — 설계 단계의 보안 결함

**[[web-security|↑ web-security]]**

> OWASP A04(2021 신설). "구현은 정확한데 설계 자체에 보안 통제가 빠진" 결함. 버그 수정으로는 못 고친다.

## 1. 개요

Insecure Design은 OWASP Top 10 2021에서 신설된 카테고리로, **설계 단계에서 보안 통제가 누락되거나
잘못 배치된** 결함을 다룬다. 이 노트의 중심 메시지는 단 하나다 — **설계 결함(design flaw)과
구현 버그(implementation bug)는 다른 종류의 문제이며, 고치는 방법도 다르다.**

다른 A0x 카테고리(인젝션, 인증 실패 등)가 주로 "어떻게 만들었나"의 문제라면, A04는 "무엇을 만들기로
했나"의 문제다. 코드 리뷰나 정적 분석으로 잡히지 않는다. 코드가 사양대로 완벽히 동작해도, 그 사양
자체가 악용 가능하면 Insecure Design이다.

## 2. 핵심 구분 — 설계 결함 vs 구현 버그

이 둘을 섞으면 "패치했는데 왜 또 뚫리지"라는 상황이 반복된다.

| 구분 | 구현 버그(implementation bug) | 설계 결함(design flaw) |
| --- | --- | --- |
| 정의 | 코드가 **의도와 다르게** 동작 | 코드가 **의도대로 정확히** 동작하는데 그 의도에 보안 통제가 없음 |
| 예시 | SQLi — 파라미터화를 빠뜨린 구현 실수 | 비밀번호 재설정에 레이트 리밋이 설계에 아예 없음 |
| 발견 | 코드 리뷰, SAST, 단위 테스트 | 위협 모델링, abuse case 분석, 아키텍처 리뷰 |
| 수정 | **패치** — 잘못된 줄을 고침 | **재설계** — 통제를 새로 설계에 넣음 |
| 비용 | 낮음 | 높음(출시 후면 최고 비용) |

```text
구현 버그:  의도 ──✗──> 코드   (코드가 의도를 못 따라감 → 패치)
설계 결함:  의도 ──✓──> 코드   (코드는 정확. 의도 자체가 취약 → 재설계)
            └─ "패치할 코드가 없다"
```

예: "쿠폰은 1회만 쓰도록 코드를 짰는데 동시 요청에 이중 적용됐다"면 구현 버그(경합 처리 누락)다.
하지만 "쿠폰을 여러 개 무한 중첩할 수 있게 **설계했다**"면 설계 결함이다 — 코드는 사양대로 잘 돌고 있다.

## 3. 대표 유형과 취약 시나리오

### 3.1 비즈니스 로직 결함

가장 흔하고 가장 자동 스캐너에 안 잡히는 유형. 도메인 규칙을 악용한다.

```http
POST /api/orders
{ "sku": "GIFT-CARD", "quantity": -5, "unitPrice": 50000 }
```

음수 수량을 허용하면 "주문"이 곧 환불(잔액 증가)이 된다. 그 외:
- **클라이언트 가격 신뢰** — 결제 금액을 프런트가 계산해 보내고 서버가 그대로 청구
  (→ [[../../../60-troubleshooting/backend/payment-amount-tampering|payment-amount-tampering]]).
- **쿠폰 무한 중첩** — 할인 적용 횟수/조합에 설계상 상한 없음.
- **포인트 경합 이중 사용** — 잔액 차감을 멱등/원자 연산으로 설계하지 않음.

### 3.2 설계상 통제 부재

흐름 자체에 보호 장치를 넣지 않은 경우.

```text
[비밀번호 재설정]
  요청 → OTP 발송 → OTP 검증 → 변경
                       └─ 시도 횟수 제한 없음 → 6자리 OTP를 무한 brute-force
```

- 비밀번호 재설정/로그인에 **레이트 리밋·속도 제한이 설계에 없음**.
- OTP 무제한 시도 → 6자리(100만 경우의 수)가 분 단위로 뚫림.
- 에러 메시지가 "존재하지 않는 계정"과 "비번 틀림"을 구분 → **계정 열거(enumeration)** 가능한 흐름.
- 결제 한도·이상거래 룰 부재 → 탈취 카드로 무제한 결제.

### 3.3 신뢰 경계 설계 오류

인가 판단을 **우회 가능한 위치**에 둔 설계.

```http
GET /admin/users
X-Admin: true        # 헤더만 보내면 관리자로 인정하는 설계
```

릴스/내부 도구에서 흔한 "특정 헤더만 있으면 관리자"식 설계가 대표적이다. 이건 구현 실수가 아니라
**인가 경계를 클라이언트가 조작 가능한 데이터에 의존하도록 설계**한 결함이다.
구현/CVE 관점의 우회는 [[broken-access-control]]에서, 여기서는 "그렇게 설계한 것 자체"가 문제다.

### 3.4 세그멘테이션 부재

평면 네트워크·단일 권한 구조 — 한 곳이 뚫리면 전부 접근된다. 테넌트 격리, 권한 분리,
네트워크 분할이 설계에 없으면 침해 1건이 곧 전면 침해가 된다.

## 4. 방어 — 왜 그렇게 하나(4구조)

### 4.1 설계 단계 위협 모델링(threat modeling)

- **왜 필요** — 코드가 생기기 *전에* "누가 무엇을 악용할 수 있나"(abuse/misuse case)를 따져
  통제를 설계에 미리 넣기 위해서다. 정상 흐름이 아니라 "악의적 사용자가 이 흐름을 어떻게 비틀까"를 본다.
- **안 하면 문제** — 출시 후에야 결함이 드러나고, 그땐 패치가 아니라 **재설계**(데이터 모델·API 계약·
  결제 흐름 전면 수정)를 해야 한다. 가장 비싼 수정이다. 예: 음수 수량을 막으려다 주문/환불/정산 도메인을
  모두 손대야 하는 경우.
- **대안** — 출시 후 침투 테스트/버그 바운티로 잡기. 동작하지만 **늦고 비싸다** — 이미 운영 데이터가
  오염됐을 수 있고, 외부 제보 보상까지 든다.
- **트레이드오프** — 초기 설계 단계에 시간과 전문성 비용이 든다. 작은 CRUD에 풀 STRIDE를 돌리면
  과투자다. → 위험한 흐름(결제/인증/권한)에만 집중하는 식으로 깊이를 조절한다.
  (위협 모델링 자체의 절차/STRIDE/DFD 깊이는 [[../../devops/security-ops/threat-modeling|threat-modeling]] 참조)

### 4.2 보안 요구사항 + 안전한 설계 패턴/레퍼런스 아키텍처

- **왜 필요** — 매 기능마다 보안 통제를 새로 발명하면 누락이 생긴다. 검증된 패턴(레이트 리밋,
  멱등성 키, 다단계 승인, 한도/상한, 서버 측 가격 산정)을 **기본 탑재**해 일관되게 적용한다.
- **안 하면 문제** — 팀마다·기능마다 통제 수준이 들쭉날쭉해진다. 결제 A엔드포인트엔 한도가 있는데
  B엔드포인트엔 없는 식의 구멍이 생긴다.
- **대안** — 각 기능에서 그때그때 보안을 즉흥 설계. 빠르지만 재현성·감사성이 없다.
- **트레이드오프** — 레퍼런스 아키텍처가 도메인에 안 맞으면 **과설계**가 된다(단순 내부 툴에
  다단계 승인 강제 등). 패턴은 위험 등급에 비례해 적용한다.

### 4.3 보조 통제

- abuse case를 **정식 요구사항**으로 백로그에 등록("정상 동작" 스토리와 같은 격으로 관리).
- 위험한 흐름에 다단계 승인·한도·이상탐지를 *설계로* 박는다(나중에 미들웨어로 덧대지 않는다).
- 서버 측 검증을 단일 진실 원천으로 — 가격·수량·권한은 클라이언트 입력을 신뢰하지 않는다.
- 인증/세션 경계는 [[authentication-session]] 패턴을 따라 설계 단계에서 확정한다.
