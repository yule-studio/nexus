# Logging & Monitoring Failures (OWASP A09) — 탐지·대응 실패

**[[web-security|↑ web-security]]**

> OWASP A09. 다른 취약점이 "뚫리는" 결함이라면, 이건 "뚫린 걸 모르는" 결함. 침해 자체보다 탐지 지연이 피해를 키운다.

## 1. 핵심 개념 — dwell time

**dwell time(체류 시간)** 은 공격자가 침입한 시점부터 방어 측이 그 사실을 **탐지한 시점까지** 의 기간이다. A09 는 다른 OWASP 항목처럼 "침입을 막는" 통제가 아니라, 이미 발생한 침입을 **얼마나 빨리 알아채고 대응** 하는가의 능력에 대한 결함을 다룬다.

dwell time 이 길수록 피해는 선형이 아니라 폭발적으로 늘어난다. 공격자는 그 기간 동안 측면 이동(lateral movement), 권한 상승, 데이터 스테이징(staging) 후 대량 유출을 수행하기 때문이다. 1 시간 안에 탐지된 침해와 6 개월간 탐지되지 못한 침해는 같은 초기 취약점에서 출발했더라도 결과가 전혀 다르다.

즉 A09 의 방어 목표는 "0 건의 침입" 이 아니라 **"탐지·대응 시간의 최소화"** 다. 완벽한 예방은 존재하지 않는다는 전제 위에서, 침해가 발생했을 때 그것을 신호로 만들고 — 신호를 보는 사람/룰을 두고 — 정해진 절차로 대응하는 것이 핵심이다.

## 2. 실제 사례 — 탐지·대응 실패가 피해를 키운 케이스

- **Target (2013)** — 보안 도구(FireEye)가 결제 시스템 악성코드에 대한 알림을 **실제로 띄웠다**. 그러나 운영팀이 이를 **무시** 했고, 약 4천만 건의 카드 정보가 유출됐다. "로그/알림은 있었는데 아무도 보지 않음" 의 대표 사례 — 탐지 도구가 아니라 대응 프로세스의 실패다.
- **Marriott/Starwood** — Starwood 예약 시스템이 약 **4년간(2014~2018) 미탐지** 상태로 침해돼, 3억 명대의 투숙객 정보가 노출됐다. 탐지 공백(detection gap)이 극단적으로 길어진 경우로, dwell time 이 곧 피해 규모임을 보여준다.
- **Equifax** — 암호화 트래픽을 검사하던 장비의 **인증서가 만료** 되어, 약 10 개월간 암호화된 트래픽 내부를 들여다보지 못했다. 그 결과 악성 활동을 놓쳤다. 탐지 룰이나 인력의 문제가 아니라 **모니터링 인프라 자체의 운영 실패** — 모니터링도 운영(operate)해야 하는 자산이라는 교훈.

세 사례의 공통점: 침입을 막는 1차 통제가 뚫린 것보다, **그 뒤의 탐지·대응 계층이 작동하지 않은 것** 이 피해를 키웠다.

## 3. 위험 유형

- **보안 이벤트를 로깅하지 않음** — 인증 실패, 접근 통제 거부, 입력 검증 실패 등 공격 신호가 되는 이벤트를 기록조차 하지 않음. → 사후 추적·탐지 불가.
- **로그가 로컬에만 존재** — 침해된 호스트의 디스크에만 로그가 있으면 공격자가 **변조/삭제** 할 수 있고, 호스트 폐기 시 함께 유실된다.
- **알림/임계값 없음** — 로그는 쌓이지만 이상 패턴에 대한 룰·임계·알림이 없어 **아무도 보지 않는다**(Target 패턴).
- **분석 불가능한 로그 포맷** — 비정형 텍스트, 일관성 없는 필드 → 상관분석(correlation)·쿼리 불가.
- **IR(사고대응) 플랜 부재** — 탐지해도 누가/언제/어떻게 대응할지 정의가 없어 골든타임을 놓친다.

## 4. 방어

### 4.1 (4구조) 왜 "보안 이벤트 구조화 로깅 + 중앙집중(SIEM) + 실시간 알림" 인가

- **① 왜 필요** — 로그인 실패 급증, 권한 거부 폭증, 비정상 접근 패턴 같은 신호를 **사람이 눈으로 보기 전에 룰이 먼저 잡아** dwell time 을 단축하기 위해서다. 구조화 로그여야 룰·쿼리가 가능하고, 중앙집중이어야 변조·유실에 강하며 여러 시스템 로그를 상관분석할 수 있다.
- **② 안 하면 문제** — 로그가 호스트마다 흩어져 비정형으로 쌓이면, 침해 신호가 데이터 안에 있어도 발견되지 않는다. Target 처럼 알림이 떠도 큐에 묻히거나, Marriott 처럼 4년간 신호 없이 흘러간다.
- **③ 대안** — 호스트별 로컬 로그 + 사람이 주기적으로 grep, 또는 단순 metric 대시보드만 보기. 그러나 둘 다 실시간성·상관분석·변조 저항이 없다.
- **④ 트레이드오프** — SIEM 인프라·스토리지·운영 비용이 들고, 임계가 느슨하면 **알림 피로(alert fatigue, false positive 홍수)** 로 진짜 알림이 묻힌다. → 임계 튜닝·우선순위화·노이즈 룰 억제로 관리. 상세는 [[../../devops/security-ops/siem|siem]] 노트에 위임.

### 4.2 (4구조) 왜 "로그에 비밀/PII 를 남기지 않는다" 가 동시에 중요한가

- **① 왜 필요** — A09 대응으로 로깅을 늘리면, 그만큼 토큰·비밀번호·주민번호·세션 ID 가 로그에 섞여 들어갈 위험이 커진다. 로그를 보호하면서 늘려야 한다.
- **② 안 하면 문제** — 평문 비밀/PII 가 로그에 남으면 **로그 자체가 새로운 공격면** 이 된다. 로그는 보통 더 넓은 권한(운영팀·SIEM·로그 백엔드)이 접근하므로, 암호화 실패(A02)·접근 통제 실패(A01)가 로그 계층에서 재현된다.
- **③ 대안** — 로깅을 줄여 비밀 노출을 피하기. 그러나 이는 탐지 능력 자체를 포기하는 것 — A09 와 정면 충돌한다.
- **④ 트레이드오프** — 마스킹/필드 화이트리스트를 적용하면 디버깅에 쓰던 원본 값이 사라진다. → **상관 추적 ID(trace/request id)** 나 값의 **해시** 를 대신 남겨 추적성과 안전성을 동시에 확보한다.

### 4.3 보조 통제

- **변조 방지** — append-only / WORM(Write Once Read Many) 스토리지, 별도 권한 도메인으로 격리.
- **보존 기간 정책** — 컴플라이언스·포렌식 요구에 맞춘 보존 기간 + 자동 만료.
- **IR 런북 + 정기 훈련** — 탐지 후 대응 절차를 문서화하고 테이블탑/실전 훈련으로 검증. 상세는 [[../incident-response/incident-response|incident-response]].
- **탐지 룰을 공격 시나리오와 연결** — 막연한 "에러율" 이 아니라 credential stuffing, 권한 상승 등 구체 시나리오에 대응하는 룰을 둔다.

## 5. 로깅해야 할 보안 이벤트

- 인증: 로그인 성공/실패, MFA 도전/실패, 비밀번호 변경·재설정, 계정 잠금
- 접근 통제: 권한 거부(403/접근 거부), 권한 상승 요청, 관리자 기능 호출
- 세션: 세션 생성/만료/무효화, 토큰 발급·폐기
- 입력 검증: 검증 실패, WAF 차단, 의심 페이로드(SQLi/XSS 패턴)
- 데이터: 대량 조회·내보내기(export), 민감 레코드 접근
- 운영: 설정 변경, 권한/롤 변경, 보안 통제 비활성화

## 6. 구조화 로그 한 줄 예시 (JSON)

```json
{
  "ts": "2026-06-15T09:14:23.512Z",
  "level": "WARN",
  "event": "auth.login.failed",
  "outcome": "failure",
  "reason": "invalid_password",
  "user_id_hash": "sha256:9f86d0...",
  "username": "j***@example.com",
  "source_ip": "203.0.113.42",
  "geo": "KR",
  "request_id": "req_01HZX8K3M2",
  "user_agent": "Mozilla/5.0 ...",
  "failed_attempts_5m": 47
}
```

```
# 비정형(분석 불가) 안티패턴 — 피할 것
2026-06-15 09:14:23 login failed for jdoe from 203.0.113.42
```

위 JSON 은 `username` 마스킹 + `user_id_hash` 로 추적성 확보 + `request_id` 로 상관분석 가능 + `failed_attempts_5m` 같은 파생 신호로 룰 작성이 쉽다. SIEM 룰은 `event=auth.login.failed AND failed_attempts_5m > 30` 같은 형태로 credential stuffing 을 실시간 탐지한다.
