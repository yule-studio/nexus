# ReDoS — 정규식 백트래킹 DoS

## 1. 증상

- 특정 입력 **하나**가 들어오는 순간 단일 요청이 CPU 한 코어를 100%로 점유하고 응답이 멈춘다. 멈춤 단위가 ms 가 아니라 **초~분**이다.
- 같은 입력이 동시에 여러 개 들어오면 모든 워커/코어가 차례로 포화되어 **전 서버 CPU 포화 → 전면 다운**. 헬스체크까지 타임아웃나서 로드밸런서가 인스턴스를 죽이고 재기동해도 같은 트래픽이 다시 잡아먹는다.
- 결정적 단서: **입력 길이가 조금만 늘어도 처리 시간이 지수적으로 폭증**한다. 30자 입력은 10ms, 35자는 300ms, 40자는 10초… 이런 식의 곡선이면 거의 ReDoS 다.
- 평소엔 멀쩡하다가 특정 사용자/특정 페이로드에서만 터지므로 "왜 이 요청만?" 으로 한참 헤맨다. APM 에서는 단일 트랜잭션이 비정상적으로 긴 self-time 을 정규식 평가 프레임에서 소비하는 걸로 잡힌다.

## 2. 원인 (root cause + 메커니즘)

대부분의 범용 정규식 엔진(PCRE, JS `RegExp`, Java `java.util.regex`, Python `re`)은 **백트래킹** 방식이다. 매칭이 실패하면 이전 선택지로 되돌아가 다른 분기를 다시 시도한다.

문제는 **중첩 수량자**(`(a+)+`, `(.*)*`)나 **겹치는 교대**(`(a|a)*`, `(a|ab)*`)다. 이런 패턴은 같은 입력을 매칭하는 경우의 수가 여러 개라서, **비매칭** 입력을 만나면 엔진이 "성공할 수도 있는 분기"를 전부 시도한다. 시도해야 할 경우의 수가 **입력 길이에 지수적**으로 늘어난다 — 이것이 **카타스트로픽 백트래킹**이다.

```regex
^(a+)+$
```

입력이 `"aaaa...a"` (전부 a) 면 빠르게 매칭된다. 하지만 끝에 매칭을 깨는 문자 하나를 붙이면:

```text
입력: "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaa!"   (a 30개 + !)
```

`$` 에서 매칭이 깨지는 순간, 엔진은 안쪽 `a+` 와 바깥 `(...)+` 가 30개의 a 를 나눠 가지는 **모든 분할 조합**을 되짚는다. a 가 한 개 늘 때마다 조합 수가 약 2배 → 35개면 수 초, 40개면 수십 초, 그 이상이면 사실상 영원히 끝나지 않는다.

```js
// JS 재현 — 노드 한 프로세스가 그대로 멈춘다
const re = /^(a+)+$/;
re.test("a".repeat(40) + "!");   // 이벤트 루프 블록, CPU 100%
```

핵심: **공격자가 거대한 입력을 보낼 필요가 없다.** 수십 바이트짜리 짧은 문자열 하나로 코어를 통째로 묶는다. 그래서 ReDoS 는 "값싼 DoS" 다.

## 3. 실제 사례

### 3.1 Cloudflare 글로벌 장애 (2019-07-02)

WAF(Web Application Firewall) 관리형 규칙에 새로 추가된 정규식이 원인이었다. 문제 패턴은 대략

```regex
.*(?:.*=.*)
```

형태로, `.*` 가 중첩되어 카타스트로픽 백트래킹을 일으켰다. 이 규칙이 전 세계 엣지에 배포되자 모든 엣지 노드의 CPU 가 정규식 평가로 **100%까지 포화**되었고, 약 **27분간** 전 세계 HTTP/HTTPS 트래픽 처리가 사실상 불가능했다. **단일 정규식 한 줄이 글로벌 장애를 낸** 교과서적 사례로, 이후 Cloudflare 는 WAF 정규식에 실행 예산(타임아웃/스텝 제한) 가드를 도입했다.

### 3.2 Stack Overflow 장애 (2016-07-20)

게시물 본문의 앞뒤 공백을 다듬는(trim) 정규식이 원인이었다. 어떤 게시물에 약 **2만 개의 연속 공백**이 들어 있었고, trim 정규식이 이 입력에서 백트래킹 폭발을 일으켜 사이트가 **약 34분간 다운**됐다. 악의적 공격이 아니라 평범한 사용자 입력이 우연히 폭발 조건을 만족한 케이스라, "사용자 입력에 닿는 정규식은 전부 잠재 위험"이라는 교훈을 남겼다.

이 두 사건은 **ReDoS 가 보안(가용성 침해 = DoS)인 동시에 순수 운영 장애**임을 보여준다. 공격자가 없어도 정상 트래픽 하나로 터질 수 있다.

## 4. 해결

1. **위험 패턴 제거** — 중첩 수량자(`(x+)+`, `(x*)*`)와 겹치는 교대를 회피한다. 필요하면 **possessive quantifier**(`a++`)나 **atomic group** `(?>...)` 로 백트래킹 자체를 차단한다.
   ```regex
   ^(?>a+)$      # atomic group — 안쪽이 한번 정해지면 되짚지 않음, 폭발 불가
   ```
2. **선형 시간 엔진 사용** — `RE2`(Go 표준, 다른 언어 바인딩 존재), Rust `regex` 처럼 **백트래킹이 없는**(DFA/NFA 기반, 입력 길이에 선형) 엔진으로 갈아탄다. 구조적으로 폭발이 불가능하다.
3. **입력 길이 상한 + 정규식 실행 타임아웃** — 정규식에 닿기 전에 입력 길이를 제한하고, 런타임이 지원하면 평가에 타임아웃/스텝 한도를 건다.
4. **사용자 제공 정규식을 그대로 실행 금지** — 검색 필터 등으로 사용자가 정규식을 직접 넣는 기능은 RE2 같은 안전 엔진 또는 별도 샌드박스/타임아웃 안에서만 실행한다.
5. **CI 정적 분석/린트** — `eslint-plugin-redos`, `safe-regex`, recheck 같은 도구로 취약 정규식을 빌드 단계에서 차단한다.

### 4.1 핵심 결정 — RE2(선형 엔진) vs 패턴 수정 + 타임아웃

**① 왜 필요한가** — 백트래킹 엔진을 쓰는 한 ReDoS 는 잠재된 채로 남는다. "근본적으로 폭발 못 하게(RE2)" 갈 것인지, "기존 엔진을 쓰되 위험을 깎아낼(패턴 수정 + 타임아웃)" 것인지 명시적으로 정해야 코드베이스 전반의 방어 수준이 일관된다.

**② 안 하면 무슨 문제** — 결정을 미루면 어떤 정규식은 안전하고 어떤 건 위험한 상태가 뒤섞인다. 새 정규식이 추가될 때마다 폭발 위험이 다시 들어오고, Cloudflare 처럼 **단 한 줄**이 전체를 무너뜨린다. 타임아웃조차 없으면 폭발한 요청이 끝날 때까지 코어가 묶인다.

**③ 대안 비교**
- **RE2 / Rust regex(선형 엔진)** — 입력 길이에 선형이 **보장**된다. 어떤 패턴을 넣어도 폭발하지 않으므로 "위험 정규식 리뷰"라는 영원한 부담에서 해방된다.
- **패턴 수정 + 실행 타임아웃** — 기존 엔진(JS/Java/Python re)을 유지한 채, 위험 패턴을 atomic group/possessive 로 고치고 평가에 타임아웃을 건다. 점진 적용이 가능하고 마이그레이션 비용이 없다.

**④ 트레이드오프** — RE2 는 근본적으로 폭발이 불가능하지만 **역참조(backreference), lookbehind 등 일부 기능을 지원하지 않고**, 엔진을 갈아끼우는 도입 비용(바인딩 추가, 기존 정규식 호환성 검증)이 든다. 패턴 수정 + 타임아웃은 도입 비용이 낮고 점진적이지만, **사람이 모든 위험 패턴을 빠짐없이 잡아야** 해서 누락 위험이 상시 존재한다 — 새로 추가되는 정규식 하나가 구멍이 된다. 실무 권장: **사용자 입력에 닿는 경로는 RE2(선형 엔진)로, 내부 고정 패턴은 패턴 수정 + 타임아웃**으로 이원화한다.

## 5. 재발 방지

- **CI 에 ReDoS 린트** 를 게이트로 건다(`safe-regex` / recheck / `eslint-plugin-redos`). 취약 패턴이 머지되지 못하게 한다.
- **사용자 입력에 닿는 정규식을 인벤토리화** 한다. 검색/필터/검증/trim 등 외부 입력을 받는 정규식 목록을 문서로 관리하고, 신규 추가 시 리뷰 체크리스트에 올린다.
- **CPU 스파이크 알람** — 단일 프로세스가 단일 코어를 장시간 100% 점유하는 패턴에 알람을 건다. 폭발이 시작되면 즉시 보이게 한다.
- **입력 길이 검증 기본화** — 정규식에 닿기 전 입력 길이 상한을 디폴트로 둔다. 폭발의 연료(긴/특정 입력)를 사전에 차단한다.
- **운영 메모리에 등재** — 같은 부류(정규식 평가 폭발)가 두 번째 잡히면 mistake ledger 로 승격해, 정규식 추가 시 자동 리뷰가 걸리도록 한다.
