# 스플릿 브레인 / 네트워크 파티션

| 문서 버전 | 작성일 | 작성자 | 주요 변경 사항 |
| --- | --- | --- | --- |
| v.1.0.0 | 2026-06-15 | web | 최초 — 파티션/이중 프라이머리/쿼럼/펜싱 |

**[[web|↑ web]]**

노드 두 대가 잠깐 서로 안 보였을 뿐인데, 회복하고 나니 같은 키에 값이 두 개다. 일부 쓰기는 흔적도 없이 사라졌다. 코드도 데이터도 안 건드렸는데 정합성이 깨졌다면, 둘 다 자기가 리더라고 믿고 양쪽에서 쓰기를 받은 **스플릿 브레인(split-brain)**을 의심하라. 분산 시스템에서 "잠깐의 단절"은 가장 비싼 장애로 번진다 — 단절 자체보다 그동안 갈라진 쓰기를 되돌리는 비용이 훨씬 크기 때문이다.

## 1. 증상 (grep용 신호 모음)

단절은 짧고, 후폭풍은 길다. 다음이 한 시기에 겹쳐 보이면 파티션/이중 프라이머리를 의심하라.

- 같은 키에 **서로 다른 값** — 어느 쪽 읽기로 가느냐에 따라 다른 답이 온다.
- 파티션 회복 후 **일부 쓰기가 사라짐** — "분명히 저장됐는데" 없어졌다는 신고.
- **중복 시퀀스 / 중복 ID** — 양쪽이 각자 같은 번호를 발급.
- 모니터링·클러스터 상태에 **"2 leaders" / "two primaries"**:
  ```
  WARNING: cluster has 2 masters (split-brain detected)
  redis-sentinel: +sdown master / +odown / failover-state-select-slave
  etcd: rafthttp: the connection ... became inactive (request timed out)
  orchestrator: DeadMaster / UnreachableMaster -> recovery: promoting replica
  elasticsearch: master_not_discovered_exception / found another master
  ```
- 클러스터 매니저 계층 전반에서: DB 복제(MySQL Orchestrator), Redis Sentinel, etcd/Consul(raft), Elasticsearch 등.

## 2. 원인 (root cause + 메커니즘)

네트워크 파티션이 클러스터를 **두 조각**으로 가른다. 각 조각은 상대를 관측할 수 없으니 "상대가 죽었다"고 판단한다. 그러면:

- 한쪽이 **새 리더를 (재)선출**하거나, 기존 리더가 **계속 쓰기를 받는다**.
- 결과적으로 양쪽 조각에 각각 프라이머리가 생긴다 → **이중 프라이머리 = split-brain**.
- 양쪽 모두 쓰기를 수락하므로, 회복 시 두 갈래의 쓰기를 한 줄로 합칠 수 없다(충돌·유실).

본질은 **CAP** 정리다. 파티션(P)이 발생한 동안에는 다음 중 하나만 가질 수 있다.

```
P 동안의 선택:
  C 우선 (CP) → 과반을 못 쥔 쪽은 쓰기를 "거부" (정합성 보존, 가용성 일부 포기)
  A 우선 (AP) → 양쪽 다 쓰기 "수락" (가용성 보존, 분기 위험 → 나중에 충돌 해소 필요)
```

`P`는 *선택*이 아니라 *현실*이다 — 네트워크는 언젠가 끊긴다. 그래서 실전 설계는 "C냐 A냐"를 미리 정해두는 일이다.

악화 트리거는 **공격적 자동 페일오버**다. 단 몇 초의 *깜빡임(blip)*에 페일오버가 과민 반응해 새 리더를 세우면, 옛 리더가 살아 돌아오는 순간 시스템 *스스로* split-brain 을 만든다.

## 3. 실제 사례 — GitHub 2018-10-21

미 동부 네트워크 허브의 **43초** 연결 단절이 방아쇠였다. MySQL 복제 토폴로지의 자동 페일오버(Orchestrator)가 이 짧은 단절을 "프라이머리 사망"으로 판정하고, **다른 데이터센터의 노드를 프라이머리로 승격**했다. 그 사이 양쪽으로 쓰기가 갈라져 들어갔다.

```
타임라인 (요약):
  T+0s    동부 허브 네트워크 단절 시작 (43초)
  T+~0s   Orchestrator: 기존 primary 도달 불가로 판정
  T+~0s   타 DC replica 를 신규 primary 로 승격 → 쓰기 분기 시작
  T+43s   네트워크 회복 → 두 곳에 갈라진 쓰기 공존
  이후     24시간+ 정합성 복구 / 수동 reconcile
```

**43초 장애가 24시간+ 데이터 정합성 복구**로 번졌다. "짧은 파티션 + 공격적 자동 페일오버 = split-brain"의 교과서적 사례다. 단절 시간이 아니라 *분기된 쓰기를 되돌리는 비용*이 진짜 피해라는 점을 기억하라.

## 4. 해결 (방어 계층)

1. **쿼럼(quorum, 과반)** — 홀수 노드로 구성하고, **과반을 쥔 조각만** 리더가 될 수 있게 한다. 두 개의 과반은 동시에 존재할 수 없으므로(3/5 노드: 한쪽이 3을 쥐면 다른 쪽은 최대 2) 이중 리더가 *원천 차단*된다. raft/paxos 기반 etcd·Consul 이 이 방식.
2. **펜싱(fencing) / STONITH** — 옛 리더가 **계속 쓰지 못하도록** 차단한다. "shoot the other node in the head". monotonic 한 펜싱 토큰을 발급해, 스토리지가 **stale 토큰의 쓰기를 거부**한다.
   ```
   리더 A: lock 획득, fencing-token=33 으로 쓰기 → OK
   (파티션) 리더 B 승격: fencing-token=34
   파티션 회복 후 리더 A 가 token=33 으로 늦게 쓰기 시도
     → 스토리지: "현재 토큰 34 > 33, 거부" (stale write 차단)
   ```
3. **리더 리스(lease) + 하이스테리시스** — 리더십에 *시간 임대*를 걸고, 페일오버에 지연·임계를 둬 깜빡임에 과민 반응하지 않게 한다. 리스는 시계 동기가 전제이므로 → [[clock-skew-auth]] 와 직결.
4. **위트니스 / 타이브레이커 노드** — 표가 갈릴 수 없도록 홀수를 보장. **2노드 구성을 피한다**(2노드는 과반 = 2라 한쪽만 죽어도 가용성이 0).
5. **중요 데이터는 일관성 우선(CP)** — 의심스러우면 쓰기를 거부하라. 회복 시에는 **멱등 재조정**으로 안전하게 합친다.

### 핵심: 쿼럼 vs 펜싱 — 왜 둘 다 필요한가 (4구조)

- **① 왜 필요** — 쿼럼은 *새 리더의 난립*을 막고(과반 없는 쪽은 승격 불가), 펜싱은 *옛 리더의 잔존 쓰기*를 막는다(stale 토큰 거부). 둘은 **서로 다른 구멍**을 막는다.
- **② 안 하면 문제** — 쿼럼만 있고 펜싱이 없으면, 새 리더는 하나여도 **옛 리더가 파티션 안에서 받아둔 쓰기**가 회복 후 새어 들어와 정합성을 깬다(GitHub 사례의 본질). 펜싱만 있고 쿼럼이 없으면, 애초에 **리더가 두 명 선출**되어 토큰 경쟁 자체가 무의미해진다.
- **③ 대안** — 단일 노드(분산을 포기)면 split-brain 자체가 없다. 또는 last-write-wins/CRDT 로 *충돌을 사후 병합*(AP). 하지만 금융 잔액·재고처럼 합칠 수 없는 데이터엔 부적합.
- **④ 트레이드오프** — 쿼럼은 **과반을 잃으면 가용성을 포기**한다(소수파 조각은 쓰기 거부 → 일부 사용자에겐 다운). 펜싱은 **인프라 복잡도·스토리지 협조**(토큰 검증 지원)를 요구한다. 두 비용을 감수하는 게 정합성 복구 24시간보다 싸다.

예시: 잔액 시스템은 쿼럼(CP)으로 소수파 쓰기를 막고, 동시에 펜싱 토큰으로 옛 리더의 늦은 출금 명령을 거부한다 — 한 겹만으로는 잔액이 마이너스로 갈라진다.

## 5. 재발 방지

- **자동 페일오버 임계/지연 튜닝** — 짧은 blip 에 페일오버 금지. 연속 N회 실패 + 최소 관측 시간을 둔다.
- **2노드 구성 제거** — 타이브레이커/위트니스 추가로 홀수 보장.
- **카오스 테스트로 파티션 주입** — `blockade`, `iptables DROP`, `tc netem` 으로 실제 단절을 정기 재현.
  ```
  # 노드 간 트래픽 강제 단절 (파티션 시뮬레이션)
  tc qdisc add dev eth0 root netem loss 100%
  # 또는
  iptables -A INPUT -s <peer-ip> -j DROP
  ```
- **분기 감지 알람** — "2 leaders" / 두 primary 동시 관측을 즉시 페이지. 늦게 알수록 분기 쓰기가 쌓인다.
- **회복 런북** — split-brain 발생 시 어느 쪽을 source of truth 로 삼고 어떻게 멱등 reconcile 할지 미리 문서화.
